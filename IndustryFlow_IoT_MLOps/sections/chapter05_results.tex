\section{Реалізовані функції та архітектура}

Платформа IndustryFlow реалізована як п'ятишарова мікросервісна система, що включає 23 контейнери Docker. Шар прийому даних забезпечує отримання показників від IoT пристроїв через HTTP API з автентифікацією на основі JWT токенів. Шар потокової обробки використовує Apache Kafka для буферизації повідомлень та Apache Spark Structured Streaming для пакетної обробки з семантикою exactly-once. Шар зберігання базується на TimescaleDB з архітектурою схема-на-тенанта, що забезпечує ізоляцію даних між клієнтами та підтримку колонкового стиснення. Шар MLOps інтегрує MLflow для відстеження експериментів та MinIO для зберігання артефактів моделей. Прикладний шар складається з FastAPI мікросервісів (API шлюз, сервіс сповіщень, сервіс ML, сервіс прийому) та React веб-інтерфейсу з візуалізацією даних у реальному часі через WebSocket.

Ключові компоненти системи працюють наступним чином: сервіс прийому валідує вхідні дані та публікує їх у топік Kafka; споживач Spark читає повідомлення з Kafka та записує до схеми відповідного тенанта в TimescaleDB; неперервні агрегати TimescaleDB автоматично обчислюють статистики для кожного сенсора; сервіс ML завантажує активну версію моделі з реєстру MLflow та генерує прогнози аномалій; сервіс сповіщень перевіряє правила детекції та створює сповіщення при їх спрацюванні.

\section{Процес розробки та технічні рішення}

Під час розробки було прийнято ряд ключових технічних рішень. Вибір архітектури схема-на-тенанта замість Row-Level Security (RLS) обумовлений необхідністю підтримки стиснення TimescaleDB --- RLS несумісний з колонковим стисненням, що унеможливило б досягнення коефіцієнту стиснення 99.98\%. Вибір Apache Kafka замість RabbitMQ обумовлений потребою у горизонтальному масштабуванні через партиціонування --- збільшення кількості партицій з 3 до 12 дало 7.7x покращення пропускної здатності Spark.

Початкова конфігурація системи (1 партиція Kafka, 1 воркер Uvicorn) забезпечувала лише 74.4 повідомлень/с. Систематичне профілювання виявило, що оновлювач кешу API Gateway споживав 80\% CPU бази даних, маскуючи справжню пропускну здатність. Після усунення цього вузького місця та оптимізації конфігурації досягнуто 552 повідомлень/с (+642\%).

Для детекції аномалій було порівняно три алгоритми: Isolation Forest, Random Forest та XGBoost. Вибір XGBoost обумовлений найкращими показниками AUC-ROC (0.8887) та F1-оцінки (0.8273) на бенчмарковому наборі даних Tennessee Eastman Process~\cite{tep_dataset, xgboost}.

\section{Труднощі та способи їх подолання}

Під час розробки виникли наступні труднощі:

\begin{itemize}
    \item оновлювач кешу API Gateway споживав 80\% CPU бази даних, що маскувало справжню пропускну здатність системи --- вирішено шляхом оптимізації частоти оновлення кешу та виділення окремого пулу з'єднань;
    \item Row-Level Security несумісний зі стисненням TimescaleDB --- вирішено переходом на архітектуру схема-на-тенанта, що забезпечує ізоляцію на рівні бази даних;
    \item Isolation Forest показав критично низьку повноту (0.0353) при високій влучності (1.0) --- вирішено вибором XGBoost з оптимальним балансом метрик;
    \item однопоточний споживач Spark обмежував пропускну здатність --- вирішено збільшенням партицій Kafka до 12, що дало 7.7x покращення.
\end{itemize}
