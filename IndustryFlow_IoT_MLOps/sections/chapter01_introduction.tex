\section{Контекст та актуальність}

Промислові підприємства стикаються з несподіваними поломками обладнання. Це коштує дорого і забирає час.
Інтернет речей в комбінації з машинним навчанням можуть допомогти, адже вони дозволяють відстежувати обладнання в реальному часі та передбачати поломки.
Традиційні системи SCADA та корпоративні платформи IoT теж виконують ці функції, але мають недоліки:

\begin{itemize}
\item Висока вартість: Рішення від SAP, Siemens, GE коштують від сотень тисяч до мільйонів доларів. Малі та середні підприємства не можуть собі цього дозволити.
\item Складна інтеграція: Впровадження SCADA займає від 6 місяців до 2 років. Потрібні спеціалісти для налаштування. Відсутність стандартів ускладнює підключення до існуючої інфраструктури.

\item Погана масштабованість: Монолітна архітектура створює вузькі місця при збільшенні кількості сенсорів. Горизонтальне масштабування потребує серйозних змін або повної заміни системи.

\item Прості сповіщення: Традиційні системи використовують фіксовані пороги для окремих параметрів. Вони не бачать складні аномалії, коли проблема виникає від комбінації параметрів. Кожен параметр окремо може бути в нормі.

\item Ізоляція даних: Коли кілька компаній використовують спільну інфраструктуру, потрібна надійна ізоляція промислових даних. Більшість традиційних систем не розраховані на багатокористувацький режим.
\end{itemize}

Ці обмеження створюють потребу в новій платформі. Вона має поєднувати доступність технологій з відкритим кодом, корпоративну надійність та машинне навчання для виявлення аномалій.

\section{Проблема}

Основні проблеми промислового Інтернету речей:

Високий поріг входу. Підприємствам потрібне надійне відстеження обладнання. Але корпоративні рішення закриті та прив'язують до одного постачальника.

Технічна складність. Створити власну систему важко. Потрібна експертиза в розподілених системах, обробці даних в реальному часі, машинному навчанні та безпеці. Це вимагає команду спеціалістів та інвестиції в розробку.

Незручні інтерфейси. Інтерфейси SCADA створені інженерами для інженерів. Операційним менеджерам та керівникам потрібно більше часу для освоєння цих інструментів. Простий інтерфейс для швидкої оцінки стану обладнання важливий.

\section{Мета та завдання}

\subsection{Мета}

Створити багатокористувацьку платформу для промислового використання. Вона має масштабуватись, працювати в реальному часі та виявляти аномалії через машинне навчання. Все на технологіях з відкритим кодом.

\subsection{Завдання}

\begin{enumerate}
    \item Спроектувати архітектуру:
    \begin{itemize}
        \item Окрема схема бази даних для кожного користувача
        \item Ієрархія даних: Компанія → Об'єкт → Обладнання → Сенсор
        \item Горизонтальне масштабування через розділи Kafka та обробники Spark
    \end{itemize}
    
    \item Зробити обробку даних в реальному часі:
    \begin{itemize}
        \item Apache Kafka для передавання повідомлень
        \item Apache Spark Structured Streaming для обробки
        \item Збирати дані за періоди (1хв, 5хв, 1год) в TimescaleDB
    \end{itemize}
    
    \item Додати виявлення аномалій:
    \begin{itemize}
        \item Три алгоритми: Isolation Forest, Random Forest, XGBoost
        \item MLflow для відстеження експериментів та версій моделей
    \end{itemize}
    
    \item Створити службу сповіщень:
    \begin{itemize}
        \item API для правил сповіщень
        \item Три режими: по порогах, по моделях, комбінований
    \end{itemize}
    
    \item Розробити API:
    \begin{itemize}
        \item FastAPI як бекенд
        \item JWT автентифікація з автоматичним search\_path
        \item Документація через Swagger
    \end{itemize}
    
    \item Налаштувати моніторинг:
    \begin{itemize}
        \item Prometheus для метрик
        \item Grafana для візуалізації
        \item Перевірки стану та сповіщення
    \end{itemize}
    
    \item Протестувати систему:
    \begin{itemize}
        \item Тести продуктивності: пропускна здатність та затримка
        \item Випробування масштабування
        \item Перевірка моделей на даних Kaggle
    \end{itemize}
\end{enumerate}

\section{Вимоги до системи}

\subsection{Функціональні вимоги}

Ф-001: Багатокористувацька архітектура

Кожна компанія має власну схему в PostgreSQL/TimescaleDB. Дані повністю ізольовані. Це дає безпеку та стиснення (економія 90-95\% місця).

Пріоритет: Критичний

Ф-002: Обробка в реальному часі

Apache Kafka та Apache Spark обробляють дані в реальному часі. Автоматично збирають агрегації за 1хв, 5хв, 1год. Затримка не більше 5 секунд від отримання до запису в базу.

Пріоритет: Критичний

Ф-003: Виявлення аномалій

Три алгоритми: Isolation Forest, Random Forest, XGBoost. Інфраструктура MLOps: сервер MLflow, реєстр моделей, версії, сховище MinIO.

Пріоритет: Високий

Ф-004: Сповіщення

Служба сповіщень має операції створення, читання, оновлення та видалення правил. Три режими: по порогах, по моделях, комбінований. Виявлювач працює в реальному часі та публікує сповіщення в Kafka.

Пріоритет: Високий

Ф-005: API

Шлюз FastAPI на порту 8000. Автентифікація JWT (токени на 7 днів). Автоматичне маршрутизування search\_path для ізоляції користувачів. Пул з'єднань. Документація OpenAPI.

Пріоритет: Критичний

Ф-006: Ієрархія обладнання

Гібридна архітектура: нормалізовані таблиці для ієрархії (Компанія → Об'єкт → Обладнання → Сенсор) та денормалізовані вимірювання з матеріалізованими шляхами для швидких запитів без рекурсивних об'єднань.

Пріоритет: Високий

Ф-007: Масштабування

Архітектура масштабується через більше розділів Kafka та обробників Spark. Без змін в коді. Тести показують лінійне збільшення пропускної здатності.

Пріоритет: Середній

\subsection{Нефункціональні вимоги}

НФ-001: Продуктивність

Асинхронне програмування (FastAPI async/await). Пул з'єднань бази. Кеш Redis (час життя 60с). Мікропакетна обробка Spark. Постійні агрегації TimescaleDB для попередньо обчислених зведень.

Пріоритет: Високий

НФ-002: Безпека

Автентифікація JWT (HS256, термін 7 днів). Хешування паролів Bcrypt (складність 12). Автоматичний search\_path для ізоляції користувачів. Параметризовані SQL-запити. Білий список CORS. Журналювання подій безпеки.

Пріоритет: Критичний

НФ-003: Надійність

Час роботи 99.99\%. Реплікація Kafka $\geq$ 2. Контрольні точки Spark. Щоденні резервні копії TimescaleDB. Автоматичне відновлення після збоїв. Перевірки стану. Політики перезапуску Docker.

Пріоритет: Критичний

НФ-004: Зберігання

Гіпертаблиці TimescaleDB з щоденними фрагментами. Стиснення для фрагментів старше 7 днів. Коефіцієнт стиснення 90-95\%. Продуктивність запитів падає не більше ніж на 20\%.

Пріоритет: Високий

НФ-005: Моніторинг

Точки збору Prometheus для всіх служб. Панелі Grafana (стан системи, бізнес-показники, продуктивність). Правила сповіщень. Збереження 30 днів.

Пріоритет: Високий

НФ-006: Сумісність

RESTful API зі специфікацією OpenAPI. Запити та відповіді JSON. Контейнери Docker. MinIO сумісний з S3. Стандартний протокол Kafka.

Пріоритет: Середній

\section{Практична цінність}

\subsection{Для кого це корисно}

Промислові підприємства отримують готове відстеження обладнання на відкритому коді. Це дає:
\begin{itemize}
    \item Менше незапланованих простоїв через раннє виявлення проблем
    \item Оптимізацію виробництва на основі даних
    \item Обслуговування до поломки через машинне навчання
\end{itemize}

Інтегратори IoT можуть використовувати платформу для клієнтів. Не потрібно будувати все з нуля.

Дослідники отримують платформу з відкритим кодом для експериментів з машинним навчанням на промислових даних. Інфраструктура MLOps вже готова.

\subsection{Технічні особливості}

Окремі технології (Kafka, Spark, TimescaleDB) не нові. Але їх комбінація має особливості:

\begin{itemize}
    \item Схема-на-користувача для TimescaleDB: Дозволяє стиснення (90-95\% економії) на відміну від захисту на рівні рядків. Цього немає в офіційній документації TimescaleDB для багатокористувацького режиму.
    
    \item Гібридна архітектура: Нормалізовані метадані та денормалізовані вимірювання з матеріалізованими шляхами. Баланс між гнучкістю та швидкістю запитів.
    
    \item Виявлення на рівні обладнання: Збираємо всі показники сенсорів за один момент часу. Це зберігає багатовимірність ознак. Більшість рішень аналізує кожен сенсор окремо, що менш ефективно.
    
    \item Гібридні сповіщення: Пороги та моделі машинного навчання в одному механізмі. Можна перемикатись між режимами без зупинки.
\end{itemize}

\section{Структура роботи}

Розділ 1. Вступ описує актуальність проблеми, мету та завдання дослідження.

Розділ 2. Огляд літератури аналізує існуючі IoT платформи (SCADA, хмарні рішення) та обґрунтовує вибір технологій.

Розділ 3. Методологія висвітлює наукові методи дослідження: аналітичний, моделювання, машинне навчання (Isolation Forest, Random Forest, XGBoost), експериментальний та порівняльний.

Розділ 4. Результати та оцінка представляє результати тестування продуктивності (пропускна здатність, використання CPU), оцінку ML моделей, ефективність стиснення TimescaleDB та мультитенантну ізоляцію.

Розділ 5. Висновки підсумовує досягнення цілей дослідження та окреслює напрямки подальшого розвитку.

\section{Методологія дослідження}

Детальний опис методології дослідження представлено у Розділі 3. У роботі застосовано комплекс наукових методів:

\begin{itemize}
    \item Аналітичний метод --- для систематичного аналізу існуючих IoT платформ та формулювання вимог до архітектури
    \item Метод моделювання --- для проєктування багаторівневої архітектури платформи
    \item Методи машинного навчання (Isolation Forest, Random Forest, XGBoost) --- для детекції аномалій у сенсорних даних
    \item Експериментальний метод --- для тестування продуктивності та ефективності стиснення
    \item Порівняльний метод --- для оцінки алгоритмів та архітектурних рішень
\end{itemize}

Відтворюваність досліджень забезпечено через інфраструктуру як код (docker-compose.yml), фіксацію версій залежностей та збереження моделей у MLflow.
