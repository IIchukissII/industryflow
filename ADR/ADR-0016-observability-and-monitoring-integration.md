# ADR-0016: Observability and monitoring integration

- **ID:** ADR-0016
- **Status:** Accepted
- **Date:** 2026-06-27
- **Project:** IndustryFlow
- **Parent:** ADR-0001 (framing — self-hosted + commercial-managed)
- **Companions:** ADR-0009 (Kubernetes/Helm packaging — deferred the monitoring stack to here)

## Context and problem

ADR-0009 packaged the platform as a self-contained Helm chart and explicitly **deferred the
monitoring stack** ("Prometheus/Grafana/Loki/exporters is a later pass"). The compose stack
ships a working observability setup (Prometheus, Grafana with two dashboards, Loki, promtail,
and node/cadvisor/postgres/redis/kafka exporters), but none of it existed on the Kubernetes
path and there were no alert rules. This ADR decides how observability is delivered on
Kubernetes for **both** deployment models of ADR-0001 (self-hosted and managed).

**Two alert planes — do not conflate them (tenancy).** This ADR governs the **system /
platform** plane only: operator-facing, tenant-agnostic infrastructure health (a service is
down, the database is unreachable, Kafka consumer lag is high). It is **distinct from the
tenant streaming / sensor-alert plane** — the alert-service's per-tenant threshold/ML
detections that flow `sensor data → rules engine → sensor-alerts topic → the tenant's schema →
that tenant's UI`. Sensor alerts are **tenant data** and live entirely inside the
tenant-isolated path (ADR-0003); they must never be routed through the shared cluster
monitoring stack, where an operator dashboard — or worse, another tenant — could see them.
The two planes have different audiences (operators vs. a single tenant), different stores
(Prometheus/Loki vs. the per-tenant schema), and different isolation guarantees.

The central tension for the platform plane: monitoring is *cluster infrastructure* shared by
every workload, not an application concern with the app's release lifecycle. Bundling Prometheus/Grafana/Loki into
the application chart couples them — every `helm upgrade` of the app touches monitoring, the
stack can't be scaled or upgraded independently, and in the managed model (where observability
is often the provider's: Grafana Cloud, AMP, Datadog) a bundled stack is dead weight or a
conflict.

## Decision drivers

- **Separation of concerns.** The monitoring backend has a different lifecycle and operator
  than the application; it should be deployable and upgradable on its own.
- **Both deployment models (ADR-0001).** Self-hosted clusters run their own stack; managed
  deployments point at a provider's. The app must integrate with whatever is present without
  carrying a backend it may not use.
- **Abstract, not test-specific.** The integration must be generic — adding a service should
  not require hand-editing monitoring config — and must use least privilege (no superuser for
  metrics), pinned images, and no `:latest`.
- **The chart stays self-contained and offline-lintable (ADR-0009).** No new umbrella-chart
  dependencies that require fetching charts from the network to `helm template`/lint.

## Decision

1. **The application chart emits *integration objects*, not a monitoring backend.** It renders
   what the cluster's monitoring stack discovers:
   - **ServiceMonitors**, generated by ranging over the app list — any service marked
     `metrics: true` gets one automatically (data-driven; a new service is scraped with no
     extra config).
   - **PrometheusRules** — platform alert rules built on always-present series (`up`, the
     exporters' `pg_up`/`redis_up`/`kafka_consumergroup_lag`) rather than app-specific metric
     names, so they stay valid as services change.
   - **Grafana dashboards** as ConfigMaps labelled for the Grafana sidecar to auto-import
     (just ConfigMaps where no sidecar exists), single-sourced from the compose dashboards.
   These CR-emitting toggles **default off** (they need the Prometheus Operator CRDs) so a
   plain `helm install` still works without the operator installed.

2. **Data-store exporters (postgres/redis/kafka) ship with the app chart** (toggleable,
   versioned images), because they are application-specific — they target *our* TimescaleDB,
   Redis, and Kafka. Cluster-generic collectors (node-exporter, kube-state-metrics, cAdvisor
   via the kubelet) come from the monitoring stack, not here.

3. **The postgres-exporter uses a dedicated least-privilege role** (`metrics_user`, granted
   the built-in `pg_monitor`), never the superuser the compose path used.

4. **The monitoring backend is run separately** — `kube-prometheus-stack` (Prometheus
   Operator + Grafana + Alertmanager) and Loki — documented under `deploy/observability/`,
   not embedded in the application chart. The chart's `serviceMonitors.labels` /
   `prometheusRules.labels` let operators match the operator's selectors.

5. **Tenant sensor/streaming alerts are out of scope and stay tenant-isolated.** They remain
   the alert-service's responsibility, delivered through the per-tenant path (ADR-0003) and the
   tenant's own UI — never through the shared monitoring stack. As a guardrail, application
   `/metrics` exposed to the platform plane must be **operational and aggregate** (request
   counts, latencies, queue depths), not per-tenant sensor values or alert contents, so
   scraping into shared Prometheus cannot leak one tenant's data to operators or other tenants.

## Alternatives considered

- **Hand-roll the full stack as plain Deployments inside the app chart.** Turnkey for a demo,
  but reinvents Prometheus/Grafana/Loki with no HA, scaling, or service discovery, ties the
  backend to the app's release, and is dead weight in the managed model. Rejected as not
  production-grade.
- **Add `kube-prometheus-stack` + Loki as chart dependencies (umbrella chart).** Gets a
  production backend, but still couples the backend to the app release, makes the chart a heavy
  umbrella, and requires `helm dependency build` (network) to lint/template — breaking the
  self-contained property from ADR-0009. Rejected.

## Consequences

### Positive

- The app is observable anywhere a Prometheus-Operator-compatible stack exists, including
  managed providers, without shipping a backend.
- Full PITR-style dashboards/alerts can grow over time by adding dashboard ConfigMaps and rules
  without touching service definitions.

### Negative

- Self-hosted operators must install `kube-prometheus-stack` + Loki once per cluster (documented)
  and flip `observability.serviceMonitors.enabled` / `prometheusRules.enabled` on — the backend
  is not turnkey out of the chart.
- Until the operator is installed, the custom resources are withheld (they would have no CRDs to
  validate against); only the raw exporter metrics are available in the interim.
